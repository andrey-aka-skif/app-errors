# Разработка

Внутреннее устройство репозитория: как собирается пакет, чем проверяется и как
попадает в реестр.

Ветка `release/v2` архивная. Новая функциональность в неё не вносится,
исправление ошибок и дальнейшая поддержка не гарантируются. Актуальная линия —
4.x в ветке `master`, сайт документации собирается только из неё.

## Требования

Node.js 22 или новее (`engines.node` в манифесте). CI прогоняет сборку на 22.x
и 24.x, публикация идёт на 24.x.

```shell
npm ci
```

## Структура исходников

```
src/
  index.js                       единственная точка входа, реэкспорт публичного API
  errorTypes.js                  перечисление типов ошибок
  AppError.js                    общий предок всех ошибок пакета
  axiosNetworkAppError.js        ошибка сети для axios
  superagentNetworkAppError.js   ошибка сети для superagent
  logicAppError.js               ошибка логики приложения
```

Помимо корневой точки входа манифест объявляет подпути `./error-types`,
`./logic`, `./axios` и `./superagent` — они ведут в тот же бандл и сохранены
ради обратной совместимости с выпусками до 2.1.0.

## Сборка

Сборку ведёт Vite в режиме библиотеки ([vite.config.js](https://github.com/andrey-aka-skif/app-errors/blob/release/v2/vite.config.js)):
из `src/index.js` получаются `dist/index.es.js` (ESM) и `dist/index.umd.cjs`
(UMD, глобальная переменная `appErrors`).

Расширение `.cjs` у второй сборки обязательно: при `"type": "module"` файл с
`.js` Node читает как ESM, и UMD-обёртка не отрабатывает.

```shell
npm run build
```

Скрипт обвязан двумя хуками: `prebuild` проверяет форматирование, `postbuild`
запускает проверку собранного пакета.

## Проверка собранного пакета

[scripts/verify-dist.js](https://github.com/andrey-aka-skif/app-errors/blob/release/v2/scripts/verify-dist.js)
проверяет то, чего не видят юнит-тесты: они гоняются по `src/` и не знают, что
с кодом делают бандлер и минификатор. Проверяются обе сборки — terser проходит
по ним независимо. Грузятся они по имени пакета, а не по пути в `dist`: ESM
через `import`, CommonJS через `createRequire`, — поэтому под проверку попадает
и карта `exports`.

```shell
npm run verify:dist
```

## Версии и публикация

Поле `version` в манифесте всегда равно `0.0.0`. Реальную версию проставляет CI
из git-тега вида `v1.2.3` в момент публикации — в репозитории версия не
хранится и вручную не правится.

Публикация идёт в GitHub Packages и запускается публикацией GitHub Release:
голый push тега пакет не выпускает. Тег создаётся самим релизом. Релиз —
единственный путь выпуска, ручного запуска у workflow нет. Упавший прогон
переигрывается кнопкой Re-run, невыпущенный тег добирается созданием релиза, а
переиздать уже выпущенную версию нельзя вовсе: реестр не даёт перезаписать
`name@version`, для этого версию сначала удаляют.

dist-tag выбирается автоматически: старшему тегу репозитория достаётся `latest`,
предрелизу — `next`, тегу неактуальной линии — `lts-<мажор>`. Выпуски этой ветки
попадают под последнее правило и получают `lts-v2`; `latest` принадлежит линии
4.x и от них не сдвигается. Правило существует затем, чтобы патч старой мажорной
линии, выпущенный после новой мажорной, не увёл `latest` назад.

Выбор считается по git-тегам, а не по содержимому реестра. Отсюда неочевидное
следствие: удаление пакетов из реестра само `latest` не возвращает — метка
появится только тогда, когда старший тег репозитория будет выпущен заново.

Имя dist-тега не должно начинаться с цифры или `v`+цифра. Реестр Gitea читает
такое имя как версию (`v2-lts` разбирается как `2.0.0-lts`) и отвечает
`400 The tag name is invalid`, уже приняв tarball: пакет оказывается
опубликован, а прогон красным. Workflow проверяет имя до сборки. История
вопроса — issue #27 и #127.

## Токены

- **GitHub** — встроенный `GITHUB_TOKEN`. Он не истекает, не требует ручного
  обновления и ограничен этим репозиторием; права выдаёт блок `permissions` в
  воркфлоу. Отдельный PAT не нужен.
- **Gitea** — PAT в секрете `GT_PACKAGES_TOKEN`. Автоматический `GITEA_TOKEN`
  не имеет авторизации на запись в реестр пакетов, документация Gitea прямо
  предписывает обходиться персональным токеном.

Gitea тянет с GitHub только рефы, релизы у неё свои и создаются отдельно.

## Поддержка архивных линий

CI/CD workflow не является частью контракта исторического релиза. Исторические
релизы не обязаны пересобираться современным workflow. Для каждой ветки
сопровождения поддерживается пересборка только последнего опубликованного
релиза.

Практически это значит, что воркфлоу в этой ветке приведён к текущему
стандарту репозитория и рассчитан на теги от 2.1.0 и новее. Попытка собрать
через него тег 2.0.5 или более ранний не поддерживается: восстанавливать ради
этого версии экшенов, рантайма и секретов на момент того выпуска — археология,
а не сопровождение.
