# Разработка

Внутреннее устройство репозитория: как собирается пакет, чем проверяется и как
попадает в реестр. Всё, что касается использования пакета, находится в
[обзоре](https://andrey-aka-skif.github.io/app-errors/guide/).

Файл лежит в корне репозитория и подключён в раздел «Разработка» сайта
документации директивой `<!--@include:-->`, поэтому ссылки в нём держатся
абсолютными: относительные не разрешатся при сборке сайта.

## Требования

Node.js 22 или новее (`engines.node` в манифесте). CI прогоняет сборку на 22.x
и 24.x, публикация идёт на 24.x.

```shell
npm ci
```

## Структура исходников

```
src/
  index.js              единственная точка входа, реэкспорт публичного API
  error-type.js         перечисление типов ошибок
  base-app-error.js     общий предок всех ошибок пакета
  errors/               классы ошибок
  builders/             сборка ошибки пакета из ошибки HTTP-клиента
```

Точка входа перечисляет экспорты явным списком: она же служит эталоном для
проверки собранного пакета.

## Сборка

Сборку ведёт Vite в режиме библиотеки ([vite.config.js](https://github.com/andrey-aka-skif/app-errors/blob/master/vite.config.js)):
из `src/index.js` получаются `dist/index.js` (ESM), `dist/index.cjs` (CommonJS)
и `dist/index.iife.js` (браузер, глобальная переменная `appErrors`). Все три
сборки минифицируются terser'ом и снабжаются картами кода.

`build.lib.fileName` задан строкой: расширения тогда подбирает Vite — при
`"type": "module"` это `.cjs` формату `cjs` и `.js` остальным.

```shell
npm run build
```

Скрипт обвязан двумя хуками: `prebuild` проверяет форматирование, `postbuild`
запускает проверки собранного пакета — содержимого и манифеста.

## Проверка собранного пакета

[scripts/verify-dist.js](https://github.com/andrey-aka-skif/app-errors/blob/master/scripts/verify-dist.js)
проверяет ровно то, чего не видят юнит-тесты, — что переживает бандлер и
минификатор:

- набор экспортов совпадает с `src/index.js`;
- значения `ERROR_TYPE` не разошлись с исходником;
- у каждого класса ошибки сохранилось имя (`instance.name`) — минификатор
  способен его срезать, если сборщик превратил объявление класса в
  присваивание анонимного выражения;
- цепочка прототипов на месте: экземпляр остаётся `BaseAppError`.

Проверяются все три сборки: terser проходит по ним независимо. Грузятся они по
имени пакета, а не по пути в `dist` — ESM через `import`, CommonJS через
`createRequire`, браузерная запуском в контексте `node:vm`, — поэтому под
проверку попадает и карта `exports`.

```shell
npm run verify:dist
```

Поведение классов и билдеров сюда не заезжает — оно покрыто тестами по `src/`,
и повторять его на сборке значило бы держать два описания одного контракта.

## Проверка манифеста

Скрипт проверяет содержимое сборки, [publint](https://publint.dev/) — манифест:
пути в `exports`, наличие файлов по ним и рассогласование ESM и CJS.

```shell
npm run lint:publish
```

## Линт и форматирование

ESLint с плоским конфигом ([eslint.config.js](https://github.com/andrey-aka-skif/app-errors/blob/master/eslint.config.js))

```

```

## Документация

Сайт собирается из двух источников: TypeDoc строит справочник API из
JSDoc-комментариев в `src/`, VitePress собирает из него и рукописных статей
готовый сайт.

```shell
npm run docs:dev
```

```shell
npm run docs:build
```

Два раздела берутся из корневых файлов и подключаются директивой
`<!--@include:-->`: «Обзор» — это `README.md`, «Разработка» — `CONTRIBUTING.md`.
Вторых копий текста нет, поэтому ссылки внутри обоих файлов должны быть
абсолютными: относительные не разрешатся при сборке сайта.

Сгенерированное (`docs/api/`, `docs/.vitepress/dist/`, `docs/.vitepress/cache/`)
в репозиторий не попадает.

## Версии и публикация

Поле `version` в манифесте всегда равно `0.0.0`. Реальную версию проставляет CI
из git-тега вида `v1.2.3` в момент публикации — в репозитории версия не
хранится и вручную не правится.

Публикация идёт в GitHub Packages и запускается публикацией GitHub Release:
голый push тега пакет не выпускает. Тег создаётся самим релизом. Релиз —
единственный путь выпуска, ручного запуска у workflow нет. Упавший прогон
переигрывается кнопкой Re-run, невыпущенный тег добирается созданием релиза, а
переиздать уже выпущенную версию нельзя вовсе: реестр не даёт перезаписать
`name@version`, для этого версию сначала удаляют.

dist-tag выбирается автоматически: старшему тегу репозитория достаётся `latest`,
предрелизу — `next`, тегу неактуальной линии — `lts-<мажор>`. Подробнее — на
странице [«Линии выпуска»](https://andrey-aka-skif.github.io/app-errors/guide/release-lines).

Выбор считается по git-тегам, а не по содержимому реестра. Отсюда неочевидное
следствие: удаление пакетов из реестра само `latest` не возвращает — метка
появится только тогда, когда старший тег репозитория будет выпущен заново.

Имя dist-тега не должно начинаться с цифры или `v`+цифра. Реестр Gitea читает
такое имя как версию (`v3-lts` разбирается как `3.0.0-lts`) и отвечает
`400 The tag name is invalid`, уже приняв tarball: пакет оказывается
опубликован, а прогон красным. Workflow проверяет имя до сборки. История
вопроса — issue #27 и #127.

Помимо GitHub в репозитории лежит зеркальный набор workflow для Gitea
(`.gitea/workflows`). Gitea тянет с GitHub только рефы, релизы у неё свои и
создаются отдельно. Сайт документации собирается только на стороне GitHub.

## Токены

- **GitHub** — встроенный `GITHUB_TOKEN`. Он не истекает, не требует ручного
  обновления и ограничен этим репозиторием; права выдаёт блок `permissions` в
  воркфлоу. Отдельный PAT не нужен.
- **Gitea** — PAT в секрете `GT_PACKAGES_TOKEN`. Автоматический `GITEA_TOKEN`
  не имеет авторизации на запись в реестр пакетов, документация Gitea прямо
  предписывает обходиться персональным токеном.
