# app-errors

> [!CAUTION]
> **Ветка `release/v2` архивная. Использовать её в новых проектах не следует.**
>
> Актуальная линия — 4.x в ветке `master`. Линия 2.x развития не получает:
> новая функциональность в неё не вносится, исправление ошибок и дальнейшая
> поддержка не гарантируются. Ветка сохраняется как эталон работы с
> поддерживаемой линией выпуска и точка восстановления для тех, кто ещё не
> перешёл на актуальную версию.
>
> **Версии обратно не совместимы.**

Npm-пакет, предоставляющий классы ошибок приложения, связанные с обращением к внешнему API и внутренней логикой.

## Установка

```shell
npm install @andrey-aka-skif/app-errors@v2-lts
```

`v2-lts` — dist-тег линии сопровождения. Он всегда указывает на последний
выпуск 2.x и не сдвигает `latest`, который принадлежит старшей версии пакета.
Годится и обычный диапазон:

```shell
npm install @andrey-aka-skif/app-errors@^2
```

Выпуски до 2.1.0 публиковались под dist-тегом `lts_v2`. Он остался висеть на
версии 2.0.5 и больше не обновляется.

## Быстрый старт

```js
import { SuperagentNetworkAppError as AppError } from '@andrey-aka-skif/app-errors'

try {
  const api = new SurveysApi()
  actualData.value = await api.surveysIdChannelsChannelIdGet(
    surveyId,
    channelId,
    OPTS
  )
} catch (responseError) {
  actualData.value = []
  error.value = new AppError(toValue(responseError))
}
```

Импорты по подпутям (`@andrey-aka-skif/app-errors/superagent`, `/axios`,
`/logic`, `/error-types`) продолжают работать: они ведут в тот же пакет и
отдают тот же набор классов.

## API

- `AppError` - базовый класс, от которого наследуются остальные. Задаёт поля `type` и `detail`.
- `LogicAppError` - класс, представляющий ошибки уровня логики приложения.
- `AxiosNetworkAppError` - класс, представляющий ошибки, полученные через библиотеку Axios.
- `SuperagentNetworkAppError` - класс, представляющий ошибки, полученные через библиотеку Superagent (а также через связку OpenApi Middleware + Superagent).
- `ErrorTypes` - перечисление типов ошибок, попадающих в поле `type`.

Оба сетевых класса представляются одинаково: `name` их экземпляров равен
`NetworkAppError`. Различать ошибки следует по полю `type`, а не по источнику.

Линия 2.x различает статусы 400, 401, 403, 404, 409 и 500. Остальные ответы —
в том числе 408, 422 и 429 — получают тип `Unknown` с сообщением «Неизвестная
ошибка»; тело ответа при этом сохраняется в `detail`. Набор распознаваемых
статусов в архивной ветке расширяться не будет, за ним следует идти в 4.x.

## Разработка

```shell
npm ci          # установка зависимостей строго по package-lock.json
npm run lint    # eslint
npm test        # vitest
npm run build   # сборка в dist/
```

`build` обвешан хуками: `prebuild` проверяет форматирование (`prettier --check .`),
`postbuild` прогоняет smoke-тест собранного пакета
(`scripts/verify-dist.js`) — юнит-тесты гоняются по `src/` и не видят того, что
делают с кодом бандлер и минификатор.

### Версионирование

Версия в `package.json` всегда `0.0.0` — это заглушка. Источник истины —
git-тег вида `vX.Y.Z`; версию в манифест проставляет CI непосредственно перед
публикацией. Руками `npm version` в репозитории не вызывается.

### Публикация

Публикация запускается **событием GitHub Release**, а не пушем тега: релиз —
преднамеренный акт с release notes, голый тег ничего не публикует.

1. Создать релиз с тегом `vX.Y.Z` на нужном коммите ветки.
2. Воркфлоу `publish.yml` собирает пакет из этого тега и публикует его.

Пересборка или переиздание уже выпущенной версии — ручной запуск
`publish.yml` через `workflow_dispatch` с указанием тега. Параметр `npm-tag` по
умолчанию равен `replay`: это паркинг-тег, который не сдвигает ни `latest`, ни
`v2-lts`.

### dist-теги

Воркфлоу вычисляет dist-тег сам:

- `latest` достаётся только старшему тегу репозитория;
- тег линии сопровождения получает `vN-lts` — для этой ветки `v2-lts`;
- предрелиз получает `next`;
- ручной запуск получает то, что указано в `npm-tag`, по умолчанию `replay`.

Правило существует затем, чтобы патч старой мажорной линии, выпущенный после
новой мажорной, не увёл `latest` назад.

### Токены

- **GitHub** — встроенный `GITHUB_TOKEN`. Он не истекает, не требует ручного
  обновления и ограничен этим репозиторием; права выдаёт блок `permissions` в
  воркфлоу. Отдельный PAT не нужен.
- **Gitea** — PAT в секрете `NPM_PUBLISH_TOKEN`. Автоматический `GITEA_TOKEN`
  не имеет авторизации на запись в реестр пакетов, документация Gitea прямо
  предписывает обходиться персональным токеном.

### Поддержка архивных линий

CI/CD workflow не является частью контракта исторического релиза. Исторические
релизы не обязаны пересобираться современным workflow. Для каждой ветки
сопровождения поддерживается пересборка только последнего опубликованного
релиза.

Практически это значит, что воркфлоу в этой ветке приведён к текущему
стандарту репозитория и рассчитан на теги от 2.1.0 и новее. Попытка собрать
через него тег 2.0.5 или более ранний не поддерживается: восстанавливать ради
этого версии экшенов, рантайма и секретов на момент того выпуска — археология,
а не сопровождение.
